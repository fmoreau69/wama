coûté une heure de diagnostic : les capacités des modèles revenaient à une forme basique après
enrichissement. Cause réelle — le Beat `model-manager-reconcile` (toutes les 2 h) tournait dans

Symptôme à reconnaître : *« mon écriture en base est correcte quand je la fais, et fausse dix
minutes plus tard »* → worker périmé, pas bug.

## 4. `select_progressif` — motif à CONSTRUIRE (demande Fabien)

Cible : proposer un modèle **léger immédiatement** (TTS, STT, traduction, assistant) pendant
qu'un **meilleur charge en parallèle**, puis basculer.

**État mesuré :**

| Axe | Où | État |
|---|---|---|
| Réponse immédiate + repli dégradé | TTS assistant (`tts_service.py`, port 8001) | ✅ éprouvé — Kokoro maintenu chaud, repli en-process |
| Bascule vers un autre modèle | assistant LLM (`views._route_model_by_context`) | ⚠️ réactive au **contexte**, pas à la latence |
| Préchargement d'un meilleur en parallèle | — | ❌ introuvable |

**Leçon architecturale à respecter** (commentaire `views.py:545`) : un thread de préchargement
Kokoro a existé **dans le process web** et a été retiré — course d'imports `accelerate` +
`HF_HUB_CACHE` global muté en concurrence. Le warm-loading a été **déplacé dans un microservice**,
pas supprimé (commit `84e2465` « warm Kokoro »). Donc : **la seconde phase doit vivre dans un
processus séparé** (microservice, ou tâche Celery sur la queue GPU), jamais dans le process qui
répond.

⚠ Sur **ce PC**, le motif a le plus de valeur mais le plus de risque : le churn de modèles Ollama
hôte est la signature du freeze instrumenté du 02/08. Sur le **serveur de production**, il devient
sûr et naturel. Concevoir pour les deux, sans figer les seuils de la machine de dev.

Briques disponibles : `quality_index` (ordonner), `prefer_loaded` (l'immédiat),
`resource_governor` (réserver).
