# CHAÎNE EXACTE : `fer` → `facenet-pytorch` → `torchvision`. Or notre torch/torchvision viennent
# de `download.pytorch.org` en versions LOCALES (`0.24.1+cu128`), absentes de PyPI. Dès qu'un
# paquet oblige pip à re-résoudre `torchvision`, le résolveur ne voit que PyPI, retombe sur
# `torchvision 0.17.2` — qui épingle `torch==2.2.2` — et le rétrogradage cascade.
#
# ⇒ `fer` s'installe avec `--no-deps` (ses dépendances réelles sont TOUTES déjà présentes :
#    vérifié par import réel, les deux backends émotions détectent). C'est exactement la
#    discipline `PIP_NO_DEPS` que WAMA déclare depuis le 2026-09-03 pour ce cas précis.
#
#        pip install --no-deps 'fer>=25.10.3'
#        pip install -r wama_lab/face_analyzer/requirements/linux.txt   # le reste
#
# C'est pourquoi `requirements_linux.txt` de la racine NOMME ce fichier sans l'inclure : un `-r`
# le rendrait installable d'un geste, et ce geste casserait le venv. Le portage de l'app
# formalisera ça en `PIP_NO_DEPS = True` sur son futur backend.
#
# Les bornes BASSES sont alignées sur ce qui est installé ET prouvé par smoke réel, pas sur des
# versions supposées. Une borne basse trop ancienne n'est pas neutre : c'est elle qui a laissé
# `fer` monter de 22.x à 25.x et CASSER l'app en silence (la classe `FER` a quitté la racine du
# paquet pour `fer.fer`).
